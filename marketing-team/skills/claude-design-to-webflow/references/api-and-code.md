## The tool stack — what's headless, what needs the Designer
| Layer | Tools | Needs the Designer tab? |
|---|---|---|
| **Data API** (`data_*`) | `data_style_tool`, `data_element_tool`, `data_element_settings_tool`, `data_component_tool` (+ `data_component_variants_tool`, `data_component_props_tool`), `data_scripts_tool`, `data_pages_tool`, `data_sites_tool`, `data_variable_tool`, `data_assets_tool`, `data_fonts_tool`, `data_whtml_builder`, `data_element_builder` | **No** — fully headless. Do all style / element / embed / code / asset / publish work here. |
| **Designer bridge** | `designer_tool`, `element_snapshot_tool`, live canvas ops | **Yes** — active + focused, else a "check the Webflow Designer MCP app" timeout. |

- **Hosted server, Streamable HTTP transport** (endpoint `/mcp` — there is no `/sse`). The surface is **~18 multi-action tools** (MCP 2.0's consolidation of 46+ single-purpose tools, same capabilities): pick the tool, then the action.
- Webflow MCP tools are often **deferred**: load their schemas in one `ToolSearch` (`select:data_style_tool,data_element_tool,data_element_settings_tool,…`). Call `webflow_guide_tool` once per session for the current capability list.
- Call **`data_agent_instructions_tool search_instructions` early** — it returns site-specific rules the team encoded.
- **Every Webflow MCP call needs `agent_id` and `session_id`** (updated 19 Nov 2026): `agent_id` is self-chosen (model|harness|short suffix, the same for the whole task); `session_id` is `start` on the first call, then the `ses_` id the server issues. `webflow_guide_tool` returns a very large text (about 110k characters): save it to a file and grep it.
- Webflow's own skills (`webflow-mcp:accessibility-audit`, `webflow-mcp:safe-publish`, `webflow-mcp:custom-code-management`, `webflow-mcp:cms-best-practices`) are optional extras where installed; teammates may not have them. Where they differ from this skill, this skill wins: publish is staging only, custom-code script limit is 2000 characters (`register_inline_script`), decorative images keep `alt=""` (updated 19 Nov 2026).

## MCP 2.0 capability quick-list (easy to miss)
- **Registered scripts** — `data_scripts_tool register_inline_script` + `add_site_script` / `add_page_script`: individually managed scripts per site/page instead of one freeform blob — read Pitfall 43 first (2000-char cap, invisible to the owner, undeletable).
- **Asset compression** — `data_assets_tool compress_assets` → webp/avif, replaces files in place (confirm first).
- **Branching** — `data_pages_tool create_branch` / `merge_branch` / `publish_branch`: git-style branches for safe iteration (→ Publish).
- **Build from HTML** — `data_whtml_builder`: raw HTML/CSS strings → native Webflow elements (next section).
- **Agent instructions** — `data_agent_instructions_tool`: site-level markdown rules auto-distributed to every connected agent.
- **Component instances** — `data_component_builder insert_in_element` / `insert_in_slot`: insert instances by component name.
- **Collection-list wiring** — a list's `source` (collectionId), `filters` and `sort` live on the **DynamoWrapper** element: `data_element_settings_tool set_settings` with `static_json` (e.g. `filters` = `[{"fieldSlug":"category-2","operator":"equals","value":"<item-id>"}]`) — repointing a duplicated page's CMS list to a new category is one call.
- **Analytics** — `data_analyze_tool`: traffic, top pages, events (requires the Analyze add-on).

## Structure path — `data_whtml_builder` (structure only)
One call turns `html` into native elements using the site's existing class names. Constraints:
- **Single root element.** No `<style>` in `html`, and no `css` param for normal styling (Native style gate). One root section per action.
- **No `@keyframes`, no custom `@media`** — Webflow breakpoints only (below). Keep keyframes / custom-media in freeform head code.
- **Quirks to fix right after the call (→ Pitfalls 22-24, 46-47):** it **drops `target="_blank"`** and leaves `href`/`rel` as raw attributes → re-set the link via `data_element_settings_tool set_settings` key `link`, then `remove_attribute`; it does **not** bind `<img src>` to the asset library → leave `<img>` out of the html and add it with `data_element_builder` (`type: "Image"`, `set_style`, `set_image_asset {image_asset_id, alt_text: ""}` in one call), or `set_image_asset` afterwards; it can **strip a class it doesn't know** (Class existence gate; recovery in Pitfall 46); text edits on its plain div Blocks need the **String child** (Pitfall 47). It keeps inline `<svg>` as native DOM, plus `<br>`, soft hyphens and curly quotes.
- Combo classes: if you ever must define one, use the full chained selector (`.base.combo`) — a bare `.combo` spawns an orphan global rule (Pitfall 22).

## Custom code via the API — freeform head/footer + HTML embeds
- **Site/Page freeform head + footer:** `data_scripts_tool` `get_site_freeform_code`/`set_site_freeform_code`, `get_page_freeform_code`/`set_page_freeform_code` (location `head`|`footer`). The setters **REPLACE the whole block** (no append) — a blind `set_site_freeform_code` nukes existing schema/analytics/reveal code, so always read → modify → write back. **The write path also 406s on ANY `<script>` tag** — even byte-identical pre-existing content already stored there (confirmed both `head` and `footer`) — while a script-free `<style>`/HTML payload with the exact same odd characters (`@property --x{syntax:'<percentage>'}`) writes fine. If the block you're touching contains a script, split it out before writing, and know the documented fallback (`register_inline_script`+`add_page_script`/`add_site_script`) can itself 404 "Custom code block not found" on some sites — leaving hand-off to the Designer's Custom Code panel as the only remaining option. → Pitfall 49.
- **HTML embeds** (`<style>`/`<script>` inside a component or page): they're `HtmlEmbed` elements — read/write via `data_element_settings_tool` `get_settings`/`set_settings`, key **`code`** (`static_text.value` = the whole `<style>…</style>`/`<script>…</script>` string). Find them with `data_element_tool query_elements` `element_filter.type:"HtmlEmbed"` (`scope_component_id` for component-nested embeds). Still snapshot the original block to a local file before a big rewrite — and because both APIs make you re-send the WHOLE block, extract the original from the live page mechanically and diff it back after publishing (→ Pitfall 33).
- **Registered site scripts are the wrong default.** `register_inline_script` caps source at 2000 chars, is invisible to the site owner (not in Site Settings → Custom Code), needs a publish per change, and can never be deleted (`delete_registered_script` 400s). Put site-wide JS in an `HtmlEmbed` inside the component that owns it. → Pitfall 43.

## Assets & fonts (headless upload — a faithful rebuild needs the real images + fonts)
- **Images:** `data_assets_tool create_asset` (file name + MD5 of the bytes) → POST the bytes to the returned presigned-S3 form → `set_image_asset` on the element by asset ID; alt text via `update_asset`. Upload first, bind by ID (whtml won't bind a raw CDN URL). Big JP/PNG → optional `compress_assets` to webp/avif (replaces the file in place — confirm first).
- **Self-hosted fonts:** `data_fonts_tool create_font` (same presigned-S3 + MD5 flow). A Google Fonts `css2` request returns ONE variable-font file per family (pass the `wght` axis range in `axes`), so a whole family is ~1-3 uploads — self-hosted is GDPR-friendlier than the Google CDN. Fallback: the user adds the family in Site Settings → Fonts by hand.

## Third-party inline embeds (Calendly & co)
A scheduler/map/form "inline widget" is an `<iframe>` you theme with the vendor's URL params (Calendly: `background_color` / `text_color` / `primary_color` / `hide_gdpr_banner`; the base profile URL renders the full event-type **catalog**, an event URL a single scheduler). Put the vendor's `<div>` + loader `<script>` in ONE `HtmlEmbed` (set its `code` via `data_element_settings_tool`), wrapped in a native styled frame (`overflow:hidden` for rounded corners; background bound to a brand token so the widget blends seamlessly). It loads fine under a visibility-gated / `autoAlpha:0` parent (the iframe still fetches).

## Getting to genuinely 1:1 (not just close) — bake the export, don't recreate it
When "pixel-identical to the design reference" is the actual bar — not "a faithful CSS approximation" — hand-built gradients/textures hit a hard ceiling on organic or dithered artwork no matter how carefully you sample colors from the reference, and coarse pixel-sampling verification will falsely report success while a human still sees the gap (banding, plastic-smooth falloff, missing texture are what sampling misses). The reliable path: export the section/card at 2x from the design tool **at its own native design coordinates**, set it as the element's `background-image` at `background-size:auto <designHeightPx>px` (never `100% 100%` — that stretch silently skews baked text the moment the live container's size drifts from the export's design size, e.g. after a grid restructure), and let the real live UI render on top at the same coordinates — unshifted, since an alignment "correction" is usually wrong and baked text will visibly ghost against the live DOM if it is. Set the live text's own `color:transparent` so its pixels come from the art (DOM text stays for a11y/SEO) instead of double-imaging against slightly different browser kerning. Verify with aligned `getBoundingClientRect()` crops, not eyeballed screenshots. → Pitfalls 59-62 for the full recipe, the alignment/ghosting traps, and the Figma-source-file quirks (`use_figma` follows whichever file is open in the desktop app, not the `fileKey` arg; `export_video` needs a top-level frame).

## Token-efficient workflow
- **One `data_whtml_builder` per section** > many element/style calls.
- **Read the page ID from the live DOM** (`document.documentElement.getAttribute('data-wf-page')`) instead of `list_pages`.
- `data_pages_tool list_pages` returns huge payloads (auto-saved to a file) → **jq/grep the saved file**; paginate with `limit`/`offset` (`total` is in `pagination`). Same for any 50k+ tool response — slice the file, never re-read it into context.
- **Query styles narrowly:** `data_style_tool get_styles` by `name_path`; add `include_breakpoints`/`include_properties` only when you need them (breakpoint queries are the heavy ones).
- **Verify with measurements, not screenshots:** JS `getComputedStyle` / `getBoundingClientRect` / CSSOM in the browser, or `element_snapshot_tool` (single-element PNG). Full-page screenshot only for the final human-facing proof — and note the in-app browser captures from **scroll-position 0 only** and Webflow **lazy-loads images**, so a full-page shot silently misses below-the-fold visuals; force `loading=eager` + scroll the page through first, or take the proof shot with a headless engine. The pane also does **not fire IntersectionObserver or scroll-driven reveals** (non-painting tab), so scroll-in animations read as "stuck hidden" there — verify those in a headless WebKit run, not the pane. → Pitfalls 31-32.
- **Batch** style/element writes via the `actions[]` array; **edit a shared embed once** instead of per page.

## Verify on staging (browser, not guesswork)
1. Publish to staging (below).
2. **Propagation lags** — re-navigate once or twice; confirm the new bundle is live by checking the page-CSS hash changed (`site.webflow.<pageId>.<hash>.opt.min.css`) or by fetching the CSS and grepping for your rule — **fetch BOTH stylesheets** (`shared` + `opt`) and strip whitespace, since a page links two and `cssRules` throws cross-origin from JS — THEN measure. → Pitfalls 21, 45.
3. Assert computed styles / rects + `read_console_messages` (expect zero errors) across the REAL scenarios (announcement banner on/off, each breakpoint, menu open, sticky at rest & scrolled). Screenshot last.
4. Chromium can't reproduce Safari bugs → flag any fixed-inside-transform / reveal-animation risk for a real-device retest. A **headless WebKit engine** (e.g. Playwright's WebKit) catches many — not all — of those render quirks the in-app Chromium browser can't, and works without a physical device. → Pitfall 19.
5. When the bar is "genuinely 1:1 to a design reference," coarse pixel-sampling and cropped screenshots can report success while a human still sees banding, falloff, or missing texture — sampling is blind to exactly the tells a human catches first. Verify with precisely-aligned `getBoundingClientRect()` crops at real scale, not eyeballed regions. → Pitfall 60.

## Build / migration playbook
1. **Recon:** `data_agent_instructions_tool` (site rules) · `data_variable_tool get_variables` (name→ID map; social.plus pre-mapped in references/variable-ids.md) · `data_style_tool get_styles name_path` (existing classes) · read the target page's live DOM. Back up any freeform block you'll rewrite (`data_scripts_tool get_site_freeform_code` / `get_page_freeform_code` → local file). For a **multi-page site or a Claude Design `.dc.html` canvas**, split frames by `data-screen-label` and map every frame onto the site's EXISTING classes and components up front (rule 6) — a page-prefixed class set is the failure mode, not the plan (Anti-pattern A10, Pitfall 70).
2. **Build** the section structure with `data_whtml_builder` using existing class names only (no `css` param), component instances for buttons/icons/cards, then style anything left with `data_style_tool`.
3. **Categorize** each remaining rule: native-eligible → `update_style`/`create_style`; code-only → freeform/embed; hybrid section-root → `--var:` in code, properties native.
4. **Bind variables** (`variable_as_value`) wherever a value matches a brand token; always keep a literal fallback in code.
5. **Rebuild JS-injected static content** as native elements; keep JS for behavior only, wrapped in `Webflow.push()`.
6. **Trim the code** — delete every rule now native (cascade conflicts are the #1 killer). Write embeds/freeform back via the API (`set_site_freeform_code` / `set_page_freeform_code` / embed key `code`) — the setters replace the whole block, so read-then-modify-then-write (Pitfall 33).
7. **Publish to staging + verify** (above). Iterate. Production ONLY when Stefan says "publish to the real website" (updated 19 Nov 2026).

## Publish
`data_sites_tool publish_site` → `publishToWebflowSubdomain: true`, `customDomains: []` = staging (`*.webflow.io`) only. Omit both and it **400s** — *"You must pass at least one valid domain id"*; the endpoint **429s** frequently → wait ~30-60 s and retry (params validate before the rate check, so a `429` rather than a `400` means your params are right). A **full publish pushes ALL pending changes** to production — do it only when Stefan says "publish to the real website", and warn him first. Before any publish, compare the site's `lastUpdated` with `lastPublished` (`data_sites_tool get_site`): unpublished changes you didn't make go out with yours, so name them. After publishing, confirm it landed (re-fetch the page and grep for a new class or text) (updated 19 Nov 2026). For isolated iteration, the branch API (`data_pages_tool create_branch → publish_branch → merge_branch` with conflict resolution) keeps work off main.

## When NOT to use
Pure Webflow work with no design/prototype input → Webflow's own skills where installed (`webflow-mcp:*`). One-off CSS tweaks with no migration. Pure Claude-artifact iteration with no Webflow target. Content writing / CMS edits → the content skills (`webflow-publisher`).
